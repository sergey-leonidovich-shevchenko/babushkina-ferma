# ADR VRENDER-002 · группы статической геометрии

**Принято:** низкую траву следующего пилота строить ArrayMesh группами по 64, управлять общей фазой vertex shader. Текущая карточка принимает сравнение и решение, дальнейшее штатное подключение остаётся отдельным этапом. [Точные результаты и все повторы](summary.json), [протокол и первичные данные](README.md).

## Причина выбора

Нужно движение принятой живописной текстуры без сотен новых кадров анимации. Три реализации используют одинаковые опоры, сетку и формулу; проверены две плотности, три повтора и два размера графического readback. CPU/группы визуально совпали, отдельные узлы отличаются не более чем на 3/255.

Числа ниже — медиана трёх повторов; update и render — медианы p95 отдельных повторов. Draw calls — медиана p50 всего кадра, **не только травы**. CPU — весь процесс, 100% означает одно ядро. У CPU указан повтор после вынесения одинаковых весов из внутреннего цикла; остальные строки — исходная серия. Оба архива сохранены.

Первый CPU-вариант имел update p95 1,718 / 4,995 мс. После оптимизации и повторного замера — 1,294 / 3,879 мс; диапазоны p95 1,285…1,296 / 3,872…3,881. Это честный более дешёвый CPU-компаратор, а не выбор слабой реализации для победы шейдера. Частоты процессора не зафиксированы; точные небольшие различия не считаются устойчивым преимуществом.

При 1024 кустах создание слоя занимает по медиане CPU 25,668 мс, отдельные узлы 70,135 мс, группы 21,765 мс. Во всех вариантах время включает загрузку одного PNG и подготовку материала; пустой контроль 5,183 мс. Эти значения показывают разовую подготовку этого участка, не холодный старт всей игры.

Наблюдаемый максимум RSS при 1024: контроль 978 MiB, CPU 981 MiB, отдельные узлы 1000 MiB, группы 986 MiB (округлено). Это отдельные процессы и редкие OS-точки; нельзя приписывать всю разницу слою или обещать экономию VRAM. Входные массивы 816 KiB для 1024 общие по составу, CPU дополнительно передаёт позиции на каждом update.

## Отклонённые варианты и ограничения

- **CPU mesh:** корректная картинка и мало узлов, но остаётся работа GDScript по каждой вершине и повторный upload. Даже оптимизированный вариант заметно дороже по update и общей CPU-доле. Архив оставлен как воспроизводимый компаратор; он не объявлен готовым low-fallback на неизвестном устройстве.
- **Отдельный CanvasItem на куст:** простой адресный контроль и более мелкий culling. Но на стрессовой плотности 1024 узла / 1164 общих draw calls, существенно больше CPU всего процесса и дороже создание. Малый собственный `_process` 0,126 мс скрывает стоимость движка, поэтому его нельзя использовать как единственный критерий.
- **Группы:** те же пиксели, меньше узлов и нагрузка процесса около контроля. Их крупные bounds могут рисовать невидимые кусты при частичном попадании группы в экран. 64 — выбранная стартовая гранулярность этого сравнения, не доказанный оптимум всей карты. Альфа-порядок сохранён последовательными группами Y/X. Высокая трава с Y-sort вокруг героя требует отдельного решения.
- **MultiMesh не выбран для этого опыта:** официальный механизм инстансинга полезен, но отдельный объект не обязан отсекаться/сортироваться как самостоятельный CanvasItem. Здесь сравнивается конкретный вариант пакетной ArrayMesh с явным порядком, а не все возможные способы Godot.

**У отдельных узлов render p95 меньше, чем у групп.** Поэтому решение не заявляет улучшения FPS или плавности, а выбирает меньшую CPU-стоимость, число объектов и разовую подготовку при одинаковом изображении. Настоящий GPU timer недоступен. Интервалы `frame_post_draw` не равны GPU completion или физическому показу. Симуляция остановлена; живой бюджет и длинная память остаются у VPERF/VRELEASE. Оснований закрывать VMAP-003, контакт с травой, тени/свет/воду или все платформы нет.

## Контракт следующего подключения

Сохранить один PNG/материал, неподвижную опору, локальные UV, расширенный bounds, управляемое игровое время и общий transform камеры. Не запекать движущийся слой в UPDATE_ONCE, не затрагивать HUD, не менять сохранённый RNG/геймплей. Пауза останавливает часы и upload; другая карта скрывает слой, возврат использует созданную геометрию. Контракт команды объекта и штатный fallback ещё принимаются своими карточками. Текущий прототип не подключён автоматически, поэтому его выключение не требует миграции сохранений.

## Первичные технические источники

Официальная документация использовалась для API и ограничений, не вместо нативного замера:

- [ArrayMesh](https://docs.godotengine.org/en/stable/classes/class_arraymesh.html): массивы геометрии и частичное обновление данных вершин.
- [MeshInstance2D](https://docs.godotengine.org/en/stable/classes/class_meshinstance2d.html): двумерный mesh и его текстура.
- [CanvasItem shader](https://docs.godotengine.org/en/stable/tutorials/shaders/shader_reference/canvas_item_shader.html): локальные вершины; встроенное TIME не следует паузе, поэтому используется собственный uniform.
- [MultiMesh](https://docs.godotengine.org/en/stable/classes/class_multimesh.html): инстансинг и ограничения общей видимости группы.
