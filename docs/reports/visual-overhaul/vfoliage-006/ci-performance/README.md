# Исправление измерения существующего performance gate

Порядок задан Team Lead после [P1 ревью](https://github.com/sergey-leonidovich-shevchenko/babushkina-ferma/pull/1#pullrequestreview-5625347281). Интеграция экспортного контракта закончена на 60171026; этот этап — отдельный смысловой QA-коммит. Игровые mechanics/resources не меняются ради измерения.

До нового валидного прогона зафиксирован `plan.json`: настоящая сцена, normal/F10, свежий профиль, cap60 после штатного startup, 3 секунды прогрева, фиксированные 10 секунд и десять полных секундных интервалов, три повтора. Сохраняются все сырые кадры/времена, конфигурация после startup, вывод/код процесса и контекст. Missing/invalid/process failures отделены от настоящего измеренного0; медленные/нулевые интервалы не исключаются. Бюджет50 сохранён. Это headless CPU gate, не аппаратный/GPU/FPS-допуск VMAP.

Для проверки механизма прежнего короткого завершения отдельно фиксируются post-startup cap, реальное время и callbacks исходной команды с480 кадрами без изменения pacing. Прежний опыт43,3 остаётся предварительной диагностикой, не приёмкой и не доказанной регрессией VFOLIAGE.

После валидного протокола normal/F10 и замороженная база PR fe591968 сравниваются последовательно на одном окружении по заранее записанному порядку. Фактические стартовые маршруты старого gate различаются; их положение записывается, а различие не приписывается автоматически только оверлею. При устойчивом F10<50 требуется предметное профилирование и отдельный production-коммит. Порог/waiver и отбор одного удачного повтора запрещены.


## Подтверждённый механизм исходного отказа

В настоящей сцене после startup наблюдался cap0 вместо CLI60. Исходный frame-limit дал ровно480 callbacks: normal —3,133с и одна опубликованная выборка, F10 —1,399с и ноль. Сырьё/время процесса/конфигурация сохранены в original480/. Это показывает, почему frame-limit не гарантирует достаточного времени публикаций. В закреплённом [Godot main.cpp](https://github.com/godotengine/godot/blob/a13da4feb8d8aefc283c3763d33a2f170a18d541/main/main.cpp#L4545) hide_print_fps_attempts изначально3, и ветка вывода пропускает первые три попытки. Поэтому отсутствие Project FPS не означает измеренный0 и не требует завершения раньше одной секунды. Конфигурация и время подтверждены отдельно от отсутствия строк.

Первый normal trace нового фиксированного протокола используется как реальная тестовая фикстура:10интервалов,555окончаний кадров в10с,55,5FPS. Это одиночная проверка коллектора, не полный gate и не основание выбирать успешный повтор. Полный набор и сравнение базы следуют плану без исключения медленных интервалов.


## Первый полный прогон исправленного gate

`fixed-gate/` содержит все шесть заранее заданных процессов, полный stdout, точные времена callbacks, по десять интервалов, post-startup конфигурацию/профиль, source/asset tree, контекст питания/нагрузки и инструментальные исходники. Все данные сохранены, включая низкие секундные интервалы. Normal:54,4 /53,4 /52,0; F10:52,1 /53,5 /51,9. Все шесть прошли прежний50, без исключения медленных интервалов или повторов до успеха. Начальный одиночный55,5 не подменяет этот полный набор.

Проверки протокола28/0 используют копии настоящего trace. Missing/invalid/process дают `average_fps=null` и отказ; настоящие полные окна0 или0,1FPS остаются валидными измерениями ниже бюджета. Ошибка процесса не скрывается `local output=$(...)`; код и сырой stdout сохранены. Чужой исторический trace не становится свежим измерением без полного реального wall time и правильного профиля.

Генерируется точная main-сцена с одним QA-наследником реального Game, остальные узлы/ресурсы сохраняются. `super._ready()` и `super._process()` не заменяются заглушками; autoplay/F10 реально активны. Cap60 восстанавливается только внутри headless QA после штатных настроек, default игры не меняется. Временные instrumentation-файлы удаляются, реальные игровые файлы проверяются до/после; низкие данные не обрезаются. Целочисленные microsecond timestamps и полное фиксированное окно позволяют независимо пересчитать каждую выборку. `startup_us` обозначает время enter-tree→ready сцены; host wall time дополнительно включает запуск/загрузку движка.

На интеграционном head60171026 [GitHub run39922602106](https://github.com/sergey-leonidovich-shevchenko/babushkina-ferma/actions/runs/39922602106) прошли architecture, game50389/0, smoke180, Wiki и обе платформенные матрицы. Только прежний performance отказал: normal160, F10missing→0. Лог сохранён в integration-ci.txt. Это независимое подтверждение открытого измерительного P1, не успешный старый gate.

QA-исправление сохраняется отдельным коммитом0.0.325. Следом нужен заранее записанный парный baseline/current опыт на одном окружении. Устойчивое падение F10 ниже50 будет основанием для профилирования и отдельного production-коммита; одиночный удачный повтор и старый предварительный43,3 не являются приёмкой. Карточка in_progress, PR draft, окончательное ревью и merge ещё закрыты.
