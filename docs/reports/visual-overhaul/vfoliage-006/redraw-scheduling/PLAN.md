# P1: фиксированный план проверки центрального redraw

Этот план записывается до новых игровых запусков после причинной кампании. Исходный [24-case профиль](../causal-investigation/README.md), его plan/SHA, обе старые отрицательные серии и P2-контроли неизменны. Повод — профилированные6–9 полных draw внутри process frame при physics catch-up; source/spans показывают повторную работу главного потока, а не только ожидание. Исправляем только этот кандидат, отдельным production commit после QA9f9c0baa.

## Предмет изменения и исходники

Точная pre-fix база —9f9c0baa44d82bfd2e9c1bbb98d0ecf4b6876a6f, версия0.0.329. Переиспользуем чистый управляемый worktree. Кандидат до финального commit — явно названный worktree delta этой же Git-базы: два скрипта `game_core.gd`/`core/game_loop.gd` по [точному patch](candidate.patch), плюс только config/version0.0.330 в project.godot. Before/after SHA этих трёх runtime файлов закреплены в plan.json до запуска. Все остальные scripts/main/assets должны совпадать; фактические runtime SHA сохраняются в каждом случае и затем сверяются с финальным production commit. Старую Git revision в context не переименовываем в будущую.

Кандидат удаляет9 центральных physics `queue_redraw`. Завершённый реальный физический такт ставит transient pending-флаг, кадровый обработчик объединяет его с прежним изменением интерполированной позы и один раз запрашивает redraw. Повторные физические шаги, порядок GameLoop, частота60Hz, max catch-up8, входные состояния, pause/UI/editor, камера, wind/filter, рендереры, картинки и saves не меняются. Нельзя получить FPS за счёт пропуска симуляции, отключения F10, снятия cap или снижения порога. Обычные редкие внешние requests от ввода не подменяются глобальным override native queue_redraw.

Точные исходники нового CPU-reader/driver/6 unit-контролей и live-probe находятся в instrumentation; их SHA входят в plan.json. Primary sampler получается из прежнего canonical source детерминированно: добавляются только три settings-маркера ready/begin/end и hold500ms **после** end для CPU-read до выхода. Process/physics/draw не оборачиваются таймерами, стековый профилировщик отсутствует. Plan SHA печатается в settings самой сцены; SHA производного sampler записывается в каждый context. Его нельзя включить в собственный plan SHA рекурсивно: проверяется точное воспроизведение из canonical SHA + pinned generator + plan SHA.

## Порядок до основных измерений

1. На прежнем коде два **функциональных отрицательных контроля** actual main — normal/F10. Один и тот же live-probe, cap10 после startup для настоящего catch-up60Hz, seed21101986, ru, свежий Codex-Redraw профиль. Они должны закончиться ненулевым результатом именно по множественному draw, а не по компиляции/engine error. Все raw/сводки сохраняются. Это функциональная проверка дефекта, не замер бюджета50.
2. Применить ровно объявленный patch, подключить тот же live-probe к обязательному run_tests и6 unit-контролей к architecture, синхронизировать версию0.0.330. Check-only не создаёт Game. Технический дефект инструмента/теста сохраняется вместе с исходником и результатом; исправление потребует явного erratum до основной кампании, без удаления старого опыта и без изменения FPS-критерия. После первого primary case source/условия/порядок не меняются.
3. Выполнить полные обязательные architecture/Game/Wiki gates. В run_tests ровно два положительных headless live-case, normal/F10. Состояния каждого:6 warmup process frames, world8, pause6, inventory6, editor6, resumed8. Все raw frames остаются; первые2 transition frames каждой фазы заранее исключены только из steady-phase функциональных asserts, не из какого-либо FPS-score. Проверить: не менее3 полных steady frames; более2 физических шагов на process frame; сумма физических delta=count/60; ровно1 draw и последнее UI-состояние; минуты идут в world/resumed и заморожены в pause/inventory/editor. Полный Game regression и неизменность прочего тела GameLoop проверяют сохранность симуляции.
4. На кандидате два дополнительных native OpenGL live-case с теми же фазами, actual main и изображением в конце каждой из5 фаз. Это проверка реального framebuffer/UI, не FPS-допуск/физический ввод/аппаратная матрица. В изолированном QA профиле pause_on_focus_loss=false, окно1152×648, method gl_compatibility. Размер фактических framebuffer записывается, Retina не выдаётся за логический размер. При отсутствии кадров/ошибке/невалидном изображении сохранить отказ и блокер; не выдавать headless PNG за native. Пользовательские профили и процессы не изменяются.
5. Все собственные тяжёлые QA/импорты/native captures завершить до основных окон. Сообщить Tech Lead об интервале без параллельного локального QA. Пауза60с перед кампанией,2с между случаями. Все24 targeted live-case (6 функциональных +12 primary +6 profiling) сохраняются независимо от результата; обычный многотысячный regression gate идёт дополнительно.

## Основное before/after и отдельный профиль

Тот же MacBookPro16,1 / Intel i7-9750H /16GiB /12 CPU /macOS15.4.1, официальный Godot4.7.1 a13, бинарный SHA из plan.json. Headless display, фактические driver opengl3 и method gl_compatibility. Physical window/focus/VSync явно отсутствуют. После настоящего startup cap60, low_processor_usage=true/sleep500µs, time_scale1, physics60/max8, delta_smoothing=true, render_loop=true, processing enabled и tree not paused. Реальные autoplay normal/F10, их исходные маршруты432,672/1160,650, locale ru, seed21101986, уникальный свежий Codex-Performance profile, без пользовательского save. Питание/thermal/host load фиксируются; настройки устройства и процессы пользователя не меняются.

Primary:3 повтора каждого normal/F10 для before/after,12 случаев. Порядок в plan.json: before-normal,after-normal,before-F10,after-F10; затем зеркальная четвёрка; затем первая. Исходный canonical protocol: прогрев3с, ровно10с и10 полных секундных bin, все callback-finish timestamp включая closing, порог50 для **каждого** из6 after-повторов. Ни низкий bin, ни плохой повтор не является missing/invalid или причиной исключения. Никакого shortened480/average0 fallback. Exit/ANSI engine errors/нарушения идентичности дают настоящий отказ.

Primary CPU: тот же owned PID на begin/end, Mach counters/timebase/query brackets, host receipt и номинально20ms snapshots game/runner/aggregate host. Reader не запускает native sample, не копирует игровую симуляцию и не меняет кадры. CPU-время всего процесса не подменяет это окно; delivery/query/closing uncertainty видима. Settings читаются в самой сцене после реального startup и на границах окна. Metadata/read-only observer имеет overhead, он одинаков для before/after и не объявляется нулевым.

После primary —6 заранее заданных **профилирующих** F10 случаев: before,after; after,before; before,after. Используются ровно прежние pinned causal timers, полный method-span trace и native sample +0.5с/3с/10ms. Для них FPS честно пересчитывается тем же валидатором, но из-за инструментального overhead не выдаётся за primary admission. Эти отказы/низкие значения также сохраняются. Цель — проверить, что повторные центральные draw исчезли, при сохранённых физике/catch-up/фактических settings, а стоимость соответствующего блока уменьшилась. Для вывода о работе сравнить именованные spans, same-window CPU и все repeats, не единичный пик или неизвестный адрес.

## Анализ и конечное решение

До/после: все18 measured случаев, bins, FPS, CPU/wall, query/receipt uncertainty, настройки, source hashes и host/power. Для profiling — counts draw/physics/process по Engine frame, excess draws/их inclusive wall, длинные gaps>33.333ms/тяжёлые>100ms и пересечение root spans без двойного учёта вложенных. Счётчики физики и реальные маршруты сохраняются; разницу normal/F10 не приписывать одному overlay. Не менять условия после удачного результата. Lossless gzip возможен только после завершения с проверкой исходных bytes/SHA/round-trip.

Если любой primary after ниже50 или невалиден, P1 остаётся открыт: показать конкретный остаточный блокер и весь набор, без повторов «до зелёного». Если все6 after выполняют прежний бюджет и live/profiling подтверждают механизм, это локальная проверка адресной правки, не аннулирование прежних отрицательных серий, не допуск всех устройств/GPU и не VMAP-003. Обязательны полный GREEN финального SHA, changed-scope rereview Tech Lead и отдельное решение Team Lead. До этого карточка in_progress, PR draft, main не сливать.
