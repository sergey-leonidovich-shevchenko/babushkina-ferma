## Что локализовано

В сохранённых473290 method spans и45175 кадровых состояниях обнаружена повторная полная отрисовка **внутри физического catch-up одного Engine process frame**. Все24 запуска содержат такие группы; максимум6–9 `_draw` за один process frame. [Сводка по каждому случаю](campaign/redraw-summary.json) содержит точные количества. Между первым и последним draw одной группы есть новые физические шаги, но нет нового `_process`/представления кадра. Суммарная inclusive wall-стоимость лишних draw перед последним в группе — около1.60–2.81с на10с диагностического окна. Это наблюдаемая стоимость, не обещанный будущий выигрыш FPS.

Пример `04-head-f10-cap60`, process frame134: gap208604µs, объединение реальных root callbacks207079µs. Между предыдущим и текущим `_process` прошли8 `_physics_process` и8 полных `_draw`; после `_process` возможна ещё одна отрисовка. CPU процесса вокруг этого gap примерно0.95–0.96 одного ядра. Полный ряд, включая замыкающий callback, сохранён в `frame-analysis.csv.gz`, исходные spans — в `stdout.txt.gz`.

В первых сравнениях head/F10 `_draw` занимает примерно4.96–5.15с inclusive wall; `_physics_process` — примерно3.78–3.89с в первых сравнениях. Вложенные `draw_ui`/`update_combat` не прибавляются к этим значениям повторно. В низких секундных bin union callbacks почти1с, CPU Game около0.95–0.98 ядра. Runner обычно около0.01, profiler имеет собственный видимый ряд. Host busy часто0.1–0.2 от12 логических CPU. Это поддерживает гипотезу конкретной работы главного потока, а не доказательство общей перегрузки устройства или спящего окна. По этим агрегатам нельзя назвать виновником пользовательское приложение.

Источник подтверждён кодом: `GameLoop.physics_process` безусловно запрашивает `game.queue_redraw()` после каждого физического шага и на ранних выходах. В закреплённом Godot a13 [SceneTree.physics_process очищает очередь deferred-вызовов](https://github.com/godotengine/godot/blob/a13da4feb8d8aefc283c3763d33a2f170a18d541/scene/main/scene_tree.cpp#L596), что позволяет выполнить CanvasItem draw между догоняющими шагами. Это соответствует первичному [Godot issue73338](https://github.com/godotengine/godot/issues/73338). Raw подтверждает механизм именно на нашем бинарном SHA и сцене; вывод не основан только на внешнем описании бага.

Кандидат на отдельный production commit: перенести **центральный запрос redraw** в кадровый `_process`, сохранив все физические обновления, их порядок, частоту и catch-up, ввод, F10 и реальные настройки pacing. Нужны live-регрессия на actual main с несколькими physics шагами за process frame и заранее зафиксированное сравнение до/после без дорогих таймеров в основном gate. Этот пакет сам по себе ещё не доказывает эффект будущей правки и не закрывает P1.

## Ограничения и сохранность

- Все post-startup/begin/end и кадровые настройки совпали с планом; overflow нет, все24 native sample завершились exit0. Физического окна, focus и VSync у headless нет: null с явной причиной. Официальный binary имеет неизвестные символы `???`; именами функций по адресам они не объявлялись. Native stacks дополняют реальные именованные script spans, а не заменяют их.
- CPU снят на begin/end того же PID, а не за весь запуск. Сохранены Mach ticks/timebase, host query brackets и receipt timestamps. Максимальная длительность одного boundary query235429ns. Доставка stdout и закрывающий callback добавляют видимую погрешность; данные не названы идеально синхронным CPU-срезом ровно10.000000с.
- [Архивный индекс](campaign/archive.json):96 файлов,73108947 исходных bytes →9139721 gzip bytes. Все round-trip и оба SHA проверены. Gzip детерминированный, mtime0; `stdout_sha256` в context относится к исходным bytes. Ни один кадр/отрицательный результат не удалён. Анализ читает gzip losslessly; старые серии не перепаковывались.
- API/check-only и13 unit-контролей выполнены до первого измерения; Game не создавали. Исходники измерения неизменны, анализ и упаковка лежат отдельно в `analysis/` и не выданы за код, записанный до кампании.
- Собственные full gates/Wiki и импорт базы закончены до серии, затем заданная пауза60с; Tech Lead подтвердил отсутствие своих параллельных QA на этот интервал. Пользовательские процессы не останавливались. Все результаты сохранены независимо от нагрузки/FPS.
