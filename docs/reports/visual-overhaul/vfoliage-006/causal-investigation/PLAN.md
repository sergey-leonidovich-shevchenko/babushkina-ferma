# VFOLIAGE-006: заранее фиксируемое расследование P1

Повод — [P1 локального бюджета](https://github.com/sergey-leonidovich-shevchenko/babushkina-ferma/pull/1#discussion_r4357267247) и [полное ревью60b3](https://github.com/sergey-leonidovich-shevchenko/babushkina-ferma/pull/1#pullrequestreview-5627955777). Этот документ, plan.json и инструментальные исходники записываются **до первого игрового измерения** новой кампании. Их точные SHA записываются в manifest и в каждый запуск; plan SHA также печатается самой игровой сценой. После начала условия и порядок не меняются.

Обе прежние серии остаются валидными отрицательными результатами. Все24 случая и исходные SHA сохраняются без изменений. Никакие новые удачные повторы, CI или результаты без cap не заменяют их. Порог50, исходный sampler и исходный plan не редактируются. Карточка in_progress, PR draft, слияние запрещено до ревью и решения тимлида.

## Данные одного и того же окна

1. Исходный callback-протокол пишет монотонные µs. Reader сохраняет точные stdout/stderr bytes, exit и host receipt timestamps. На begin/end немедленно читает CPU **того же PID** через публичный proc_pid_rusage V2. Query begin/end и задержка доставки маркера видимы; CPU не выдаётся за математически точный синхронный срез без погрешности. End печатается до дампа; затем child живёт ещё500ms вне окна, чтобы CPU-end читался до выхода. CPU всей загрузки не подменяет CPU10секунд.
2. Каждые20ms read-only наблюдатель пишет Mach CPU ticks, timebase, CPU ns, RSS/footprint, pageins, disk bytes game и собственных runner/sample. Host CPU ticks и load average — агрегаты без имени/аргументов пользовательских приложений. Нельзя делать вывод о конкретном внешнем виновнике по одному load average. Native sample PID и его нагрузка сохраняются как overhead.
3. Внутри того же окна буферизуются начало/конец реальных Game process, physics, draw, zero-argument draw_* и update_*(delta), а также WorldBackground.draw. Генератор перечисляет фактические методы каждого дерева; он не копирует/подменяет игровую симуляцию. Таймеры содержат inclusive spans: вложенные нельзя суммировать как независимую стоимость. Лимит500000 spans/states, overflow явно делает диагностическое покрытие неполным. Дамп происходит после CPU-end, все записи сохраняются.
4. Фиксированная native stack-съёмка собственного Game PID начинается через500ms после begin, длится3с с интервалом10ms, в каждом из24 случаев. Её время/выход/сырьё сохраняются. Статистические стеки не доказывают покрытие каждой длинной паузы, поэтому полное окно дополняет method-span trace. У официального stripped binary возможны `???`: по ним нельзя придумывать имя функции. Sampling и таймеры добавляют overhead; вся кампания — диагностика, а не FPS-допуск неизменённой игры.
5. Lossless gzip допустим только после завершения с сохранением SHA исходных bytes и с проверкой round-trip. Исходные старые файлы не сжимаются/не переписываются. Ошибки инструментов, cap/settings, недостающие маркеры и неполные серии сохраняются с явным статусом; низкий FPS не является причиной invalid.

CPU ri_user_time/system_time измеряется Mach absolute-time ticks: используем числитель/знаменатель mach_timebase_info, сохраняем исходные значения и не предполагаем1:1. Основание: [Apple XNU task_power_info_locked](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/task.c), [публичные интерфейсы Recount](https://github.com/apple-oss-distributions/xnu/blob/main/doc/observability/recount.md) и локальные SDK sys/resource.h/libproc.h/mach headers. Размер структурыV2 и неединичный timebase проверяются тестом.

## Анализ и критерии причинности

- Пересчитать все24 случая, все bin и все frame gaps. Отдельно показать cap60 primary FPS (включая ниже50), cap0 диагностический FPS, CPU/wall с границами query, длительности/inclusive стоимость методов, host CPU/load, настройки и sample overhead. Разбор длинного кадра: gap>33.333ms; тяжёлого>100ms. Ни один кадр/случай не исключается для улучшения результата.
- Сопоставлять gap с пересечением span-интервалов, соседними CPU-снимками и состоянием движка. Вложенные spans сводятся объединением интервалов для верхнего уровня; renderer-секции показываются отдельно. 20ms CPU-снимок даёт приближённую привязку, не точный CPU каждого кадра.
- Конкретная стоимость Game становится кандидатом на production-правку только при повторяющихся дорогих одноимённых span/стеках, согласованных с низкими интервалами и CPU. Минимальное подтверждение — не менее трёх наблюдений в двух повторах; единичный пик или неизвестный адрес не доказательство. Исправляется только профилированная причина существующего F10, отдельным commit с сохранением симуляции и последующим заранее описанным сравнением. Без конкретной причины код игры не меняется.
- Pacing/ожидание: сравнивать cap60/0 пары, CPU и реальную работу внутри gap, статистические sleep/wait стеки. Стабильное улучшение cap0 само по себе не оправдывает снятие ограничения и не закрывает бюджет. Для причинного вывода нужны повторные согласованные наблюдения, а не один удачный запуск.
- Внешняя нагрузка/планировщик: проверять временную связь с host CPU/own-process CPU/thermal и gap без соответствующей работы Game. Отличать от engine cost вне скриптов; при недостатке символов/данных причина остаётся неустановленной. Никакие процессы пользователя не завершаются.
- Если низкие FPS не воспроизведены, историческая причина остаётся недоказанной; старые отрицательные результаты не аннулируются. Если причина внешняя либо не локализована — сохранить доказательства и назвать конкретный блокер, без повторов «пока зелёное». После этой фиксированной кампании новых условий без нового отдельного плана нет.

Предварительная компиляция QA-наследников `--check-only` и13 unit-контролей выполняются без игровых измерений. Их лог и точные исходники входят в пакет. Затем новая серия проходит весь заявленный порядок. Результаты и вывод оформляются отдельно после сбора; исходный план не дописывается задним числом.
