## Исходная гипотеза

`SceneTree.process_frame` испускается до `_process`; `CanvasItem.queue_redraw` откладывает сборку команд. Старый helper вызывает `RenderingServer.force_draw(false)` сразу после `process_frame`. Гипотеза: он рендерит прежние команды, а обработчик `frame_post_draw` завершает одноразовый SubViewport и отключает его до свежей сборки. Кандидат ждёт обычный `frame_post_draw`, не вызывая ранний принудительный рендер. Так была сформулирована гипотеза до пробы; контролируемый старый/новый запуск и полный X11 принятого head описаны выше.

Источники контракта движка: [process_frame](https://docs.godotengine.org/en/stable/classes/class_scenetree.html#class-scenetree-signal-process-frame), [queue_redraw](https://docs.godotengine.org/en/stable/classes/class_canvasitem.html#class-canvasitem-method-queue-redraw), [frame_post_draw](https://docs.godotengine.org/en/stable/classes/class_renderingserver.html#class-renderingserver-signal-frame-post-draw).

## Контролируемое воспроизведение

`tools/qa/ground/color_patch_sync_probe.gd` наследует настоящий capture helper. Игровая сцена не запускается: объект игры не добавляется в дерево и освобождается после пробы. Отдельный SubViewport заполняется зелёным, его обновление отключается. Перед возобновлением helper из `process_frame` контрольный узел запрашивает красный draw и одноразовое обновление. Завершение по `frame_post_draw` отключает кеш так же, как это делает `WorldBackground`.

Старый метод извлекается без редактирования из `tools/qa/ground/color_patch_capture.gd` в коммите `e79a3a870eb683e09e4ce3c5dfd02e6ea67e9777`, SHA256 `0da370807958fc5e5a826641bf8e0c976579631939d308aa3ae3998555fff325`. Внешняя историческая точка входа переопределяет только этот метод. Кандидат исполняет текущий унаследованный метод без дублирования его алгоритма в тесте.

Проверка во всех случаях требует красный кадр. Оркестратор принимает намеренный старый код 1 только вместе с зелёным PNG, фактом запроса красного и отсутствием свежего draw перед чтением. Для кандидата нужны код 0, красный PNG и порядок запрос → draw → завершение → чтение. PNG сверяется независимо через Pillow. Коды инфраструктуры, ошибки движка, неверный размер, версия или порядок событий отвергаются. Четыре случая выполняются в отдельных последовательных процессах; фиксируются исходники, PNG, журналы и хеши. Это проверка синхронизации, не FPS.

Следом тот же CI запускает полный существующий collector/verifier. Контролируемая проба сама по себе не заменяет реальные пары грунта. Если старый helper не воспроизводит заявленный дефект, гипотеза не считается доказанной и критерий не ослабляется.

Две новые регрессии проверяют реальный формат метаданных и обязательный отказ на ALSA/GLES/ошибке скрипта даже при старом коде 1.
