# Ревью через GitHub Pull Request

Порядок принят пользователем 23 октября 2026 года. В GitHub используется Pull Request (PR); «мердж-реквест» обозначает ту же заявку на слияние.

## Передача готовой реализации

1. Developer Agent работает в `codex/<id>-<имя>`, сохраняет отдельные коммиты по смыслу и выполняет `TESTING.md`. В PR указывает проблему, полученное поведение, границы изменения, проверки, известные ограничения и доказательства нативной проверки, когда она нужна.
2. Ветка публикуется сразу для ревью. PR направлен в `main`; готовый код передаётся Tech Lead Agent с URL и точным head SHA. Если обязательная проверка ещё идёт, PR помечается draft и это явно указывается. Зелёный локальный тест не означает зелёный GitHub CI.
3. Tech Lead Agent проверяет корректность, читаемость человеком, имена, структуру, отступы, форматирование, производительность, память, граничные случаи, тесты и документацию. Комментарии объясняют назначение самостоятельных смысловых блоков и причины решений; пересказ очевидной строки не заменяет понятный код.
4. Замечания оставляются у конкретных строк самого PR: приоритет P0–P3, проблема, последствия, направление исправления и проверяемый критерий готовности. Обязательные исправления отделяются от предложений.
5. Сводка идёт Team Lead Agent. Тимлид возвращает задачи Developer Agent в порядке приоритета. Developer Agent не обходит эту очередь и не принимает собственную работу за независимое ревью.
6. Исправления публикуются в том же PR обычными коммитами и push. Доказательства и проверки обновляются по объёму изменения; ревью повторяется для нового head SHA. Одобрение старого SHA не разрешает слияние изменённого кода.
7. После одобрения текущего SHA, закрытия обязательных замечаний, успешных обязательных проверок и решения Team Lead Agent выполняется обычное слияние PR в `main`. Отдельного разрешения пользователя только из-за обновления `main` не нужно.

Если все агенты используют один GitHub-аккаунт, GitHub может не разрешить формальный self-approval. Это не повод имитировать независимое одобрение: ревьюер записывает явный вердикт и SHA в обсуждении PR, а Team Lead Agent фиксирует решение. Требование отдельного ревью остаётся. Ограничения доступа или CI явно указываются; их не обходят.

26 октября 2026 пользователь прямо поручил агентам самостоятельно проводить весь этот цикл, включая решения, приёмку, обычное слияние и учёт, без повторного обращения к владельцу за рутинным апрувом. Постоянное разрешение относится к принятым изменениям после независимого ревью текущего SHA и решения Team Lead; автор не принимает собственную работу вместо ревьюера.

## Карточка, ветки и публикация

GitHub Actions уже запускаются на `pull_request`. Checkout получает историю Git: нативные проверки читают исходники закреплённых прошлых commit, поэтому shallow checkout одного head недостаточен. Лимиты времени учитывают полный architecture/игровой набор; увеличение лимита не заменяет успешный результат. Репозиторные права и branch protection этим изменением не перенастраиваются.

До завершения ревью статус карточки — `in_progress`. В `result` записываются фактический результат реализации, URL PR, проверенный SHA и состояние ревью. `done` означает принятую и влитую задачу. Прежние доказательства и ID сохраняются; готовность к ревью не разблокирует зависимые задачи как будто реализация уже принята.

`Task-Complete: <ID>` относится к принятой задаче, промежуточные исправления его не получают. Существовавший до смены процесса trailer не переписывается в опубликованной истории; решающими остаются PR, статус карточки и решение о слиянии. После принятого merge удаляется только полностью влитая ветка этой задачи, не занятая worktree. Незавершённые и чужие ветки сохраняются.

Для ревью публикуется ветка каждой задачи. Старый прямой push `main` после десяти задач заменён публикацией через принятые PR. `tools/task_batch.py status` остаётся средством исторического учёта; `publish` не служит обходом ревью. Force push и переписывание опубликованной истории без отдельного указания запрещены.

## Сообщение ревьюеру

Передавать URL PR, ID/ссылку карточки, base и head SHA, краткое описание, изменённые подсистемы, результаты с названиями команд и путями к отчётам, ограничения, состояние CI. Сообщать, если head обновлён после передачи. Запрашивать замечания в PR и сводку через Team Lead Agent; не просить ревьюера менять общую рабочую папку незаметно для ветки и автора.

## Звук и музыка

Когда согласованной задаче нужны аудиофайлы, Developer Agent обращается к Music Agent. Задание содержит игровое событие/сцену, художественное настроение, длительность, loop/one-shot, начало и конец, необходимые варианты, формат, ограничения громкости и место использования. Полученные файлы проходят проверку и интеграцию в игру в соответствующей ветке. Музыкальный заказ не расширяет сам по себе приоритет первой локации.
