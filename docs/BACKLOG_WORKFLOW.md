# Работа по файлу бэклога

[План: 6 эпиков и 50 задач](backlog/2026-10/README.md) хранится в репозитории. GitHub issues создавать не требуется. Текущие статусы, зависимости и подтверждения выполнения находятся в [`backlog.json`](backlog/2026-10/backlog.json); читаемый README строится из него, чтобы два описания не расходились.

Дополнительные согласованные эпики перечислены в [общем указателе](backlog/README.md). Например, [WATER](epics/water-2026-10/README.md) имеет собственные 15 карточек и ручной журнал в Markdown; он не меняет исходные 50 задач и не притворяется частью их автоматической проверки. Для такой задачи ветка тоже привязана к ID (`codex/water-01-audit-baseline`), а статус, приёмка и подтверждения меняются в её файле. Ограничение одной активной задачи действует между планами тоже. Подготовка отдельного эпика допускает ID `WATER-00`.

## Как брать задачу

1. Выбрать один пункт `ready`, прочитать результат и критерии, сверить исходное состояние с текущим кодом. План не доказывает наличие бага. Рекомендуемый первый пункт — OPT-01.
2. Проверить зависимости: все блокеры должны быть `done`, выбор дизайна/доступ к устройству подтверждены. Подтверждённое внешнее условие убрать из `needs`, историю записать в `result`. Связи с завершёнными блокерами сохранять.
3. Проверить чистоту checkout, выполнить `git fetch origin` и сравнить локальную `main` с `origin/main`. Локальная `main` может содержать ещё не опубликованный пакет: не сбрасывать её и не заменять удалённой веткой. При новых удалённых изменениях выполнить обычный merge и проверки; при возможности достаточно fast-forward. Новую ветку создавать от актуальной локальной `main`: `codex/<id-строчными>-<короткое-имя>`, например `codex/opt-02-storage-frame-budget`. Ветка обозначает ID файла, не номер GitHub issue.
4. Поставить `in_progress` и выполнить `python3 tools/project_backlog.py --write`. Одновременно в работе один пункт. Если нужная ветка уже существует, продолжать её после проверки; не создавать дубликат и не переключаться поверх чужих правок.

```sh
git status --short
git fetch origin
git switch main
# При изменениях origin/main сначала объединить историю без reset/rebase опубликованных коммитов.
python3 tools/task_batch.py status
# Далее git switch -c и точное имя из карточки выбранной задачи.
python3 tools/project_backlog.py --write
```

Статусы: `backlog` — ждёт очереди; `ready` — подготовлена; `blocked` — есть явные препятствия; `in_progress` — делаем сейчас; `done` — результат принят и подтверждён. Статус не вычисляется автоматически: после завершения блокера проверяем соседние задачи и явно переводим подходящие в Ready. Проверка не позволит Ready при незавершённых зависимостях. S/M/L обозначают относительный объём, не срок; L можно разбить на этапы до реализации. Новые пожелания оформлять отдельно, не увеличивать текущую задачу бесконечно.

Для живописного пилота использовать [ограниченную очередь VRELEASE-001](reports/visual-overhaul/vrelease-001/README.md), Wiki → Задачи → «Первый участок · статичный показ» и `python3 tools/pilot_rollout.py --next`. Её дополнительные условия усиливают канонические зависимости, а не заменяют их. Полные критерии карточки обязательны; частичный пилот не даёт `done`. После изменения графа выполнить `python3 tools/pilot_rollout.py --write` и пересобрать Wiki, после обычной смены статуса состав не переписывать.

## Как завершать

- Записать воспроизведение и данные до изменения. Для `investigation`/`validation` допустим вывод «гипотеза не подтвердилась», если есть данные; лишнее переписывание не требуется.
- Новую графику сохранить отдельно от игровых ресурсов и самостоятельно выбрать вариант по правилам `AGENTS.md`. Сохранить три ракурса предметов, светлый интерфейс и другие ограничения из карточки.
- Проверить профильные и отрицательные сценарии, обновить соответствующие тесты, руководство, обучение и QA при изменении механики. Изменение документации само по себе не требует фиктивного игрового этапа.
- Выполнить `tools/check_architecture.sh` и `./run_tests.sh`; для Wiki дополнительно её `pnpm check`. Нативные измерения и физические устройства не подменять headless-прогоном или размером окна.
- В `result` записать результат, commit/отчёт и реально выполненные проверки. Неподтверждённый ручной пункт не считается выполненным из-за зелёного общего набора. Только после приёмки всех критериев поставить `done` и пересобрать README.
- Делать отдельные коммиты по смыслу. В последний коммит полностью принятой задачи добавить trailer `Task-Complete: OPT-02` с её точным ID; промежуточные коммиты его не содержат. Сразу влить готовую задачу в локальную `main` и удалить только её полностью влитую локальную ветку через `git branch -d`, если её не использует другой worktree. Незавершённые и чужие ветки не удалять.
- Публиковать `main` после каждых 10 завершённых задач. Несколько коммитов одного ID считаются одной задачей; служебные изменения и merge без trailer не увеличивают счётчик. До десятой задачи результат уже находится в локальной `main`, но ещё не в GitHub: это прямо указывать в отчёте. Не требуется ждать push, чтобы принятая и влитая локально задача получила `done`.
- Обычные commit, merge, fast-forward и push в `origin/main` постоянно разрешены пользователем; отдельное подтверждение не требуется. Пакетный порядок установлен 18 октября 2026 года вместо прежнего push каждого коммита. Отдельная просьба пользователя о push разрешает отправить неполный пакет. Force push и переписывание опубликованной истории требуют отдельного указания.

## Учёт пакета и публикация

```sh
# После проверок и приёмки, в ветке задачи:
git commit -m "OPT-02: сократить повторную сборку сетки" -m "Task-Complete: OPT-02"
git switch main
git merge --ff-only codex/opt-02-storage-frame-budget
git branch -d codex/opt-02-storage-frame-budget
python3 tools/task_batch.py status

# Только когда накопилось 10 задач: проверки TESTING.md, затем
python3 tools/task_batch.py publish
```

Если fast-forward невозможен, обычный merge разрешён; после объединения повторить проверки. Перед публикацией пакета обязательны `tools/check_architecture.sh`, `./run_tests.sh` и профильные проверки из `TESTING.md` (в том числе Wiki, если она менялась). Команда `publish` сама тесты не запускает. При PR указывать локальный ID и ссылку на карточку; `Closes #…` не нужен.

Счётчик выводится из уникальных Git trailers в `origin/main..main`: отдельного изменяемого файла состояния нет, перезапуск агента ничего не сбрасывает. `status` читает только Git и не обращается к сети. `post-commit` показывает этот статус и ничего не отправляет. `publish` при 0–9 задачах оставляет пакет локально; при 10 и более делает fetch, повторно считает задачи, требует чистую `main` без расхождения с сервером и выполняет обычный push только `main`. Если другой процесс уже опубликовал пакет, повторной отправки нет. Неудачный push сохраняет все неопубликованные задачи; причину исправить, проверки повторить при изменениях и явно сообщить о задержке. Новые удалённые коммиты требуют объединения истории и повторной проверки. Удалённые ветки автоматически не удаляются.

Новый отсчёт начинается с опубликованной `main` `be3c28d` (18 октября 2026 года); прежние задачи задним числом не считаются. Эта служебная смена правил не является одной из десяти задач бэклога.

Эпик готов после своих детей; общий план — после приёмки всех задач. Старый реестр TECH_DEBT.md сохраняет факты и историю, OPT сохраняет прежние номера. 320 запланированных сценариев не становятся пройденными при переносе описания.

## Проверки плана

```sh
python3 tools/project_backlog.py --write
python3 tools/project_backlog.py
python3 tools/test_project_backlog.py
```

Все команды работают без сети, токенов и внешних изменений. Проверяются число задач исходного плана, ссылки, ID, критерии, циклы, блокировки и синхронность читаемого файла. Проверка структуры не доказывает выполнение механики. Источники и наша интерпретация отдельно описаны в [исследовании](backlog/2026-10/RESEARCH.md).
