Текущие статусы, зависимости и подтверждения выполнения находятся в [`backlog.json`](backlog/2026-10/backlog.json); читаемый README строится из него, чтобы два описания не расходились.

Подготовка отдельного эпика допускает ID `WATER-00`.

## Постановка отдельных идей

Одна самостоятельная игровая идея — один тематический эпик или одна небольшая задача. Сборные эпики по дате обзора с 22 октября не создаём. Сначала проработать сценарий, состояния, границы и собственные предметные этапы; выбрать группу и связать идею с настоящим эпиком. Сохранить прежние ID/статусы и переходы старых ссылок при переносе. Оценка пользы/интереса/стоимости — основание для обсуждения прототипа, а не автоматическое Ready. [Контракт Wiki](WIKI_DEVELOPMENT.md).

## Как брать задачу

1. Выбрать один пункт `ready`, прочитать результат и критерии, сверить исходное состояние с текущим кодом. План не доказывает наличие бага. Рекомендуемый первый пункт — OPT-01.
2. Проверить зависимости: все блокеры должны быть `done`, выбор дизайна/доступ к устройству подтверждены. Подтверждённое внешнее условие убрать из `needs`, историю записать в `result`. Связи с завершёнными блокерами сохранять.
3. Проверить чистоту checkout, выполнить `git fetch origin` и сравнить локальную `main` с `origin/main`. Локальная `main` может содержать ещё не опубликованный пакет: не сбрасывать её и не заменять удалённой веткой. При новых удалённых изменениях выполнить обычный merge и проверки; при возможности достаточно fast-forward. Новую ветку создавать от актуальной локальной `main`: `codex/<id-строчными>-<короткое-имя>`, например `codex/opt-02-storage-frame-budget`. Ветка обозначает ID файла, не номер GitHub issue.
4. Поставить `in_progress` и выполнить `python3 tools/run.py planning.project_backlog --write`. Одновременно в работе один пункт. Если нужная ветка уже существует, продолжать её после проверки; не создавать дубликат и не переключаться поверх чужих правок.

```sh
git status --short
git fetch origin
git switch main
# При изменениях origin/main сначала объединить историю без reset/rebase опубликованных коммитов.
python3 tools/task_batch.py status
# Далее git switch -c и точное имя из карточки выбранной задачи.
python3 tools/run.py planning.project_backlog --write
```

Статусы: `backlog` — ждёт очереди; `ready` — подготовлена; `blocked` — есть явные препятствия; `in_progress` — делаем сейчас; `done` — результат принят и подтверждён. Статус не вычисляется автоматически: после завершения блокера проверяем соседние задачи и явно переводим подходящие в Ready. Проверка не позволит Ready при незавершённых зависимостях. S/M/L обозначают относительный объём, не срок; L можно разбить на этапы до реализации. Новые пожелания оформлять отдельно, не увеличивать текущую задачу бесконечно.

Для живописного пилота использовать [ограниченную очередь VRELEASE-001](reports/visual-overhaul/vrelease-001/README.md), Wiki → Задачи → «Первая локация · статичный пилот» и `python3 tools/run.py planning.pilot_rollout --next`. Её дополнительные условия усиливают канонические зависимости, а не заменяют их. Полные критерии карточки обязательны; частичный пилот не даёт `done`. После изменения графа выполнить `python3 tools/run.py planning.pilot_rollout --write` и пересобрать Wiki, после обычной смены статуса состав не переписывать.

## Как завершать

Приоритет с 19 октября 2026 — первая `overworld` целиком до VMAP-003, по главе Wiki «Первый живописный участок». Новые механики, игровые эпики идей и другие карты не подмешивать; предложения хранить отдельно. Пилот проверяет способ, VMAP-001 задаёт ведомость всей первой карты, VMAP-002 — её атмосферу, VMAP-003 — окончательную приёмку. Выбирать адресную графику только по этой ведомости, не запускать весь каталог VBUILD/VACTOR/VPLANT. Совместимость существующих механик — обязательная регрессия, не их расширение.

- Записать воспроизведение и данные до изменения. Для `investigation`/`validation` допустим вывод «гипотеза не подтвердилась», если есть данные; лишнее переписывание не требуется.
- Новую графику сохранить отдельно от игровых ресурсов и самостоятельно выбрать вариант по правилам `AGENTS.md`. Сохранить три ракурса предметов, светлый интерфейс и другие ограничения из карточки.
- Проверить профильные и отрицательные сценарии, обновить соответствующие тесты, руководство, обучение и QA при изменении механики. Изменение документации само по себе не требует фиктивного игрового этапа.
- Выполнить `tools/check_architecture.sh` и `./run_tests.sh`; для Wiki дополнительно её `pnpm check`. Нативные измерения и физические устройства не подменять headless-прогоном или размером окна.
- В `result` записать результат, commit/отчёт и реально выполненные проверки. Неподтверждённый ручной пункт не считается выполненным из-за зелёного общего набора. Готовность к ревью оставляет карточку `in_progress`; `done` — после приёмки критериев, ревью и слияния.
- Делать отдельные коммиты по смыслу, публиковать ветку и открывать GitHub PR в `main`. Передавать URL и точный head SHA в Tech Lead Agent. Замечания у строк PR и сводка идут Team Lead Agent, который возвращает доработки Developer Agent. Исправления требуют повторного ревью нового head; подробнее — [CODE_REVIEW.md](CODE_REVIEW.md).
- До принятия текущего SHA и решения Team Lead Agent не сливать ни в локальную, ни в удалённую `main`. После принятого PR сохранить `Task-Complete: OPT-02` с точным ID, поставить `done` и пересобрать README. Удалять только полностью влитую ветку задачи, если её не использует другой worktree. Незавершённые и чужие ветки не удалять.
- Ветки для PR отправляются сразу; `main` публикуется через принятые PR. Это порядок с 23 октября 2026, заменивший прямой push пакета из десяти задач. Постоянное разрешение на обычные действия в принятом порядке сохраняется; повторное подтверждение только из-за `main` не нужно. Force push и переписывание опубликованной истории требуют отдельного указания.

## Передача PR и публикация

```sh
# После проверок, в ветке задачи:
git commit -m "OPT-02: сократить повторную сборку сетки"
git push -u origin codex/opt-02-storage-frame-budget
# Открыть PR с base main и передать URL/head SHA Tech Lead Agent.
# Слияние — после ревью текущего SHA, проверок и решения Team Lead Agent.
```

Перед передачей обязательны `tools/check_architecture.sh`, `./run_tests.sh` и профильные проверки `TESTING.md`, включая Wiki при её изменении. У PR указываются локальный ID и карточка; `Closes #…` не нужен. При обновлении base/head сохранять обе работы обычным merge без переписывания опубликованной истории; проверки повторять по изменённому объёму и обязательным hooks. Не объявлять прерванный прогон успешным.

Исторический `python3 tools/task_batch.py status` считает уникальные trailers в `origin/main..main`; отдельного файла счётчика нет. `post-commit` показывает статус и ничего не отправляет. Прежний `python3 tools/task_batch.py publish` реализует пакетный прямой push и остаётся служебным инструментом истории, а не маршрутом обхода PR-ревью. Открытые PR, текущий SHA и решение ревьюера теперь определяют готовность к слиянию. Ошибки публикации, доступа и CI явно указывать; непрошедшую проверку не обходить.

Пакетный отсчёт начинался с `be3c28d` 18 октября 2026 года. Переход к обязательным PR 23 октября сохраняет эту историю и прежние ID.

Эпик готов после своих детей; общий план — после приёмки всех задач. Старый реестр TECH_DEBT.md сохраняет факты и историю, OPT сохраняет прежние номера. 320 запланированных сценариев не становятся пройденными при переносе описания.

## Проверки плана

```sh
python3 tools/run.py planning.project_backlog --write
python3 tools/run.py planning.project_backlog
python3 tools/run.py planning.test_project_backlog
```

Все команды работают без сети, токенов и внешних изменений. Проверяются число задач исходного плана, ссылки, ID, критерии, циклы, блокировки и синхронность читаемого файла. Проверка структуры не доказывает выполнение механики. Источники и наша интерпретация отдельно описаны в [исследовании](backlog/2026-10/RESEARCH.md).
