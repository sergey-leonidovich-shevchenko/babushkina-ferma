# Центр разработки в Wiki

Wiki открывается значком рядом с игрой. Раздел **«Разработка»** объединяет эпики, идеи, очередь проработки и задачи. Для работы с планами пользователю не нужно открывать Markdown и искать карточки по папкам.

## Обзор первой локации

Первый пункт меню **«Первая локация · прогресс»** открывает `#/development/first-location`: выбранные эпики VIS/WATER, текущие карточки в работе, точный прогресс очереди статичного пилота и шесть этапов приёмки до VMAP-003. Данные читаются из действующего каталога, обновляются кнопкой и каждые 30 секунд. Обзор сохраняет общий список эпиков и их редакционные группы.

Счётчики обычных эпиков относятся ко всем их карточкам; VBUILD/VACTOR/VPLANT явно помечены как весь каталог, состав первой карты уточняет VMAP-001. VMAP показывает только 001…003, VRELEASE — 001…005. Общий процент всей локации не вычисляется по каталогу: приёмку подтверждает VMAP-003. При статическом просмотре показан режим сохранённой версии; недоступная или устаревшая очередь не выдаёт ложный прогресс.

## Пользовательский процесс

1. **Эпики.** Карточки сгруппированы по направлениям и показывают фактический прогресс. В меню карточки можно перенести эпик в другую группу. «Управление группами» создаёт группу; для переименования сначала выберите её в фильтре. Группировка не дублирует задачи и не меняет их владельцев.
2. **Идеи.** «Новая идея» сохраняет название, замысел, направление и замечания. У каждой идеи постоянный номер. Статьи IDEA из редакционного реестра также появляются здесь. У идеи можно открыть подробности, изменить текст или отложить её.
3. **Одобрение.** «Одобрить» переводит предложение в **«На проработку»**. Можно начать проработку, скопировать задание агенту или вернуть идею в предложения. Изменения сохраняются в проекте, а не только в памяти вкладки.
4. **После постановки.** Когда агент действительно создал карточки, выберите их эпики в идее и нажмите «Задачи созданы». Идея уйдёт из очереди и сохранит ссылки на эпики. Это не закрывает реализацию дочерних задач.
5. **Задачи.** Поиск по ID, названию и результату, фильтры плана/статуса, отдельная карточка с зависимостями, приёмкой, проверками и подтверждениями. Большой список раскрывается по 50 строк. Исходные статусы показываются без автоматического пересчёта зависимостей.

Кнопка «Обновить» читает свежие планы и решения. При конфликте двух вкладок запись отклоняется с объяснением: обновите данные и повторите действие. Ошибка сохранения оставляет введённый текст в форме. Если открыт статический сайт без локального сервера, отображается режим просмотра и кнопки записи недоступны; запустите значок Wiki для редактирования.

## Источники и сохранение

- [`wiki/planning/state.json`](../wiki/planning/state.json) — единственная редакционная запись идей, решений, заметок, истории, групп и переназначений эпиков. Файл версионируется в Git и не находится в `dist`, `.cache` или localStorage. Пересборка и перезапуск его не сбрасывают.
- [`wiki/planning/sources.json`](../wiki/planning/sources.json) — явный реестр планов и ожидаемого числа карточек. Каталог читает обе текущие схемы JSON и редакционные Markdown-карточки. Стандартные новые планы с `backlog.json` или `TASKS.md` в отдельных папках `docs/epics`/`docs/backlog` подхватываются автоматически; явная запись имеет приоритет и задаёт желаемые ID, название и группу. При изменении согласованного объёма зарегистрированного плана обновляется `expected`. Отдельные подпапки и нестандартная структура регистрируются явно.
- Статусы, критерии и подтверждения существующих игровых задач остаются в их канонических карточках. Wiki собирает их в единый экран; отдельных копий статусов не хранит. Импорт не закрывает задачи и не исправляет зависимости самостоятельно. Противоречивые статусы карточки/указателя или потерянный источник отклоняются явно.
- [`WIKI-001`](backlog/wiki-workspace-2026-10/README.md) фиксирует приёмку этого центра. Исторические планы и рисунки сохраняют свои адреса.

Запись состояния выполняется временным файлом, синхронизацией и атомарным переименованием; ревизия предотвращает потерю изменений, lock исключает параллельные записи разных процессов. Ошибка не подменяется пустым состоянием. Обычные commit/push и принятие идут по [актуальному порядку PR](CODE_REVIEW.md): ветка задачи → GitHub PR base main → ревью текущего head Tech Lead → решение Team Lead. До принятия main не изменяется, карточка остаётся in_progress с URL PR; пакетный publish не используется. Сам сайт не выполняет Git-команды.

## Памятка агенту постановки

Прочитать `wiki/planning/state.json`, взять идею со статусом `approved` или `refining`, сохранить её ID и замечания. Через работающую Wiki доступна та же очередь: `GET /__wiki/planning/queue`, включая готовый текст задания. Не считать исходный `proposed` одобренным и не объявлять план реализованным.

Сверить существующие системы и соседние планы. Для постановки можно использовать ID `IDEA-NNN-00`, для дочерних карточек — отдельные постоянные ID. Записать границы, зависимости, результат и индивидуальную приёмку; зарегистрировать источник в `sources.json`, добавить запись в [указатель бэклогов](backlog/README.md). После подготовки связать идею с существующими эпиками через Wiki. Для программной редакции использовать API с актуальной ревизией; прямое изменение JSON допускается только с сохранением чужих решений и проверкой схемы.

`GET /__wiki/planning` возвращает каталог и актуальное состояние. `POST /__wiki/planning/change` принимает JSON с `revision` и явным заголовком `X-Wiki-Planning: 1`. Действия: `create-idea`, `edit-idea`, `set-idea-status`, `plan-idea`, `create-group`, `rename-group`, `move-epic`. Обязателен loopback Host и совпадающий Origin, если он передан. API не принимает пути файлов и не пишет в игровые слоты. Штатный launcher обновляет старый сервер, если у него нет API планирования.

Прямое поручение пользователя добавить обязательную механику можно сразу оформить согласованным эпиком, без фиктивной IDEA и повторного одобрения. HURT и PERK используют этот путь: подготовка done отделена от будущей реализации, каждому новому перку дана собственная задача в тематическом эпике; старые ID и очередь сохраняются.

## Отдельный эпик каждой идеи

С 22 октября 2026 одна самостоятельная механика получает свой эпик с названием по существу и тематической группой. Небольшой законченный объём можно оформить одной задачей; существующие ID при уточнении сохраняются. Разные идеи не складывать в «ежедневный» или общий IDEA-эпик. Дата остаётся у отчёта об обзоре, не определяет владение игровыми задачами.

[Каталог самостоятельных идей](../wiki/articles/idea-feature-epics.md) связывает статьи с настоящими эпиками. В `docs/epics/ideas/idea-NNN/` находятся паспорт и TASKS; `sources.json` регистрирует отдельный план с его группой и ожидаемым числом карточек. Сначала фиксируются границы первого выпуска, единый владелец состояния, отмена/загрузка, конкретные части и их зависимости; затем интеграция и приёмка. Не нарезать каждую механику одинаковыми общими заголовками без предметного результата.

Четыре старых дневных эпика разделены на 40 самостоятельных. Исходные 120 игровых ID и статусы сохранены, добавлены 111 предметных этапов; три завершённые редакционные карточки находятся в WIKI. Их старые URL продолжают вести к прежним ID через `legacy-development-links.json`. Отчёты и Git сохраняют историю, архивные TASKS больше не импортируются как копии.

## Оценки идей

[Методика](../wiki/articles/idea-assessment-method.md) разделяет пользу, интерес, соответствие, связи, стоимость, риск и знакомость. `wiki/planning/assessments.json` хранит обоснование, аудиторию, критерий малой пробы, дату и границу проверенного сравнения. Первые 40 оценок и по десять новых оценок обзоров 22 и 23 октября — дизайнерские гипотезы. Не подменять ими одобрение или результаты теста аудитории.

Каждую новую проработанную идею снабжать такой оценкой. При отсутствии проверенного аналога знакомость остаётся пустой; отсутствие записи не равно нулю. В Wiki есть просмотр и сортировка оценок. Сохранение решения пользователя через state.json не пересчитывает баллы и не стирает обоснование. После прототипа оценки пересматриваются с реальными наблюдениями. Даты обзоров не становятся новыми игровыми эпиками.

## Ограниченные очереди внедрения

VRELEASE-001 добавляет к существующему разделу задач фильтры «Очередь» и «Этап». Очередь `village-pilot` связывает 52 уже существующих ID; глава «Первый живописный участок» ведёт прямо к её этапам. Это представление общего каталога, не ещё один план и не копия статусов. Прогресс и блокеры обновляются через действующий API. Дополнительные условия пилота видны в карточке и копируемом тексте агенту, даже если карточка открыта через общий поиск.

Ручная область/границы — `docs/reports/visual-overhaul/vrelease-001/plan.json`. `python3 tools/pilot_rollout.py --write` строит топологическое замыкание в соседний `queue.json`, проверяемый по сигнатуре канонических зависимостей при сборке Wiki. В `sources.json` раздел `queues` регистрирует этот файл; API идей и `state.json` не меняются. При смене только статусов регенерация не нужна. При изменении состава/зависимостей обновить очередь, проверить её и пересобрать Wiki. Неизвестная очередь/этап либо потерянная зависимость не подменяются глобальным списком.

Очередь рекомендует только `ready` без открытых условий, `backlog` предлагает подготовить, `blocked` автоматически не повышает. Критерии канонических карточек сохраняются целиком; непроверенный широкий охват не получает `done` из-за маленького пилота. Следующая очередь движения разворачивается отдельно после статичной приёмки; текущая не принимает игровой перенос или FPS.

## Проверки

`pnpm --dir wiki check` выполняет экспорт, проверку импортированных планов, TypeScript, сборку и Node-тесты. `wiki/tests/planning.test.mjs` проверяет полноту планов, зависимости WATER, чтение JSON/Markdown, атомарность, создание/редактирование, одобрение, группы, историю, конфликты ревизий, связь с эпиками, перезапуск и реальные HTTP-отказы. Все записи в тестах идут в отдельную временную папку. Затем обязательны архитектурный gate и полный игровой набор из [TESTING.md](../TESTING.md). Браузерная приёмка отдельно проверяет основные переходы, поиск, клавиатуру и узкий экран.
