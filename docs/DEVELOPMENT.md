# Разработка

## Требования

- macOS, Linux или Windows;
- Godot 4.7.1;
- Git;
- Python 3 для проверки документации и воспроизводимой генерации аудиоресурсов.

На macOS совместимая сборка Godot уже может находиться в `tools/Godot.app`. В CI бинарник 4.7.1 загружается явно, поэтому локальная и серверная среды используют одну версию движка.

## Запуск проекта

Из редактора откройте `project.godot` и запустите `main.tscn`. Из терминала на macOS:

```bash
tools/Godot.app/Contents/MacOS/Godot --path .
```

Специальные режимы помогают проверять интерфейс без ручного прохождения стартовых экранов:

Машинный аудит геометрии восьми ключевых UI-поверхностей и инвентаризацию текстовых вызовов можно обновить отдельно:

```bash
tools/Godot.app/Contents/MacOS/Godot --headless --path . --script res://tools/generate_ui_layout_audit.gd
python3 tools/update_ui_visual_manifest.py
```

Результат сохраняется в `docs/reports/ui_layout_audit.json`; требования и текущая очередь описаны в [UI-аудите](UI_AUDIT.md). Обновитель визуального manifest использует Pillow, сохраняет exact SHA для диагностики и устойчивый perceptual-отпечаток для CI.

Изолированный полигон запускается аргументом `--debug-playground`. На стенде `F1–F3` меняют время, погоду и сезон; `F4` выдаёт тестовый набор; `F5–F6` создают врага и выбирают уровень; `Page Up/Page Down` меняют семейство; `F7` прокручивает состояния животных; `F8` телепортирует; `F9` меняет квест; `C` включает коллизии; `F10` возвращает в игру. `Space` ставит симуляцию на паузу, `.` пропускает один кадр, `H` показывает хитбоксы, `P` — маршруты AI, `I` — инспектор. Основные команды продублированы кнопками; клик по существу показывает его состояние. Панель хранит график последних 120 значений FPS.

Для поиска невидимых стен без ухода с проблемного места используйте `F10` (`F11` оставлена совместимым дублем). `DebugOverlaySystem` кэширует только видимую часть сетки и получает причину каждой клетки через `NavigationSystem.walkability_reason`, поэтому цвет совпадает с фактическим движением. Размеры 12/24/48/96 берутся из общего `SpatialGridSystem`; режим 24×24 совпадает с тайлами карты, а контур 48×48 показывает блок из четырёх тайлов. Noclip обходит проверку только внутри `NavigationSystem.move`, но не меняет ответ инспектора. Недоступные будущие инструменты редактора отображаются серыми и не изменяют состояние мира.

Левая сворачиваемая панель F10 перечисляет все задания в порядке прохождения. `i` показывает подробности без изменения мира; `✓` выполняет полный QA-маршрут через `DebugMissionSystem`: закрывает зависимости, удовлетворяет особые условия, вызывает штатную сдачу в `QuestSystem`, выдаёт реальные награды и переводит источник целевого предмета в опустошённое состояние. Так проверяется не декоративная отметка, а итоговое состояние, которое затем попадёт в обычное сохранение.

`DebugObjectInspectorSystem` независимо от renderer-а собирает нормализованные runtime-кандидаты текущей локации и выбирает верхний объект по видимому `bounds`, приоритету слоя и площади. `DebugObjectInspectorRenderer` использует эти же данные для чёрного контура в мировых координатах и INFO-карточки в экранных координатах. Добавляя новый тип мирового объекта, зарегистрируйте его позицию, полный визуальный прямоугольник, коллизию и полезные технические поля в инспекторе; renderer не должен повторно вычислять игровое состояние.

Встроенный `LevelEditorSystem` открывается клавишей `F12` или включённой кнопкой `КОНСТРУКТОР` в F10. Пока он активен, `_physics_process` не продвигает симуляцию, но `RenderSystem` продолжает собирать живую локацию и добавляет четыре дизайнерских слоя через `LevelEditorRenderer`. Каталог и правила якорей принадлежат отдельному `LevelEditorAssetCatalogSystem`: папки `source`, мастера и preview-листы скрыты, а миниатюры загружаются только для пяти видимых строк. Клик по каталогу включает постоянную кисть; непрерывный мазок заполняет все клетки 24×24 алгоритмом Брезенхэма и записывается одной операцией истории. Полный контракт описан в [памятке конструктора](LEVEL_EDITOR.md).

Пользовательские ограды принадлежат `FenceSystem`: данные хранятся как JSON-безопасные клетки 24×24 внутри `estate.expansion.fences`, а не как пиксельные прямоугольники. `FenceRenderer` выводит строгий атлас 8×5 и вычисляет соединительный модуль из четырёхбитной маски соседей. Калитка занимает две клетки. Навигация запрашивает ту же структуру через `blocks_position`, поэтому рисунок, сохранение и коллизия не расходятся. Исходный художественный лист нормализуется воспроизводимым скриптом `tools/build_fence_atlas.py`.

Рабочее состояние редактора намеренно хранится в metadata сцены и не смешивается с пользовательским сохранением RPG. Кнопка `СОХР.` пишет черновик в `user://level_designs`, а `ЭКСПОРТ` создаёт переносимые JSON и PNG в `res://level_designs`. Формат `babushkina-ferma-level-draft` версии 3 дополнительно сохраняет якорь `tile`, `bottom` или `center` и семейство автотайла; старые документы остаются совместимыми. Сериализация принадлежит `scripts/editor/level_editor_document_store.gd`, поэтому кисти и обработка мыши не зависят от JSON и файловой системы. Импорт текущей локации использует нормализованные данные `DebugObjectInspectorSystem`, поэтому новый тип мирового объекта автоматически становится доступным для дизайнерской разметки после регистрации в инспекторе.

## Обязательная проверка

Перед каждым коммитом выполните:

```bash
tools/check_architecture.sh
./run_tests.sh
```

Первая команда контролирует размеры `game_core`, контекста, renderer и suites, утечки отрисовки в фасад, пробельные ошибки, обязательные документы и локальные Markdown-ссылки. Она также рекурсивно ищет новые мировые изображения, мёртвые preload и попытки хранить уникальные размеры в renderer; fixture аудитора запускается автоматически. Для подробного отчёта размеров используйте `python3 tools/check_world_sprite_manifest.py --json-report`. Вторая команда импортирует ресурсы в headless-редакторе и запускает все GDScript-наборы. Успех подтверждается строкой вида `TESTS: N passed, 0 failed`.

Git hook `pre-commit` повторяет quality gate, а `post-commit` отправляет успешный коммит в GitHub. GitHub Actions запускает те же проверки на push и pull request.

## Версионирование задач

`VERSION` — единственный источник SemVer приложения. Проект начинает публичную нумерацию с `0.0.1`. Одна завершённая задача оформляется отдельным коммитом; перед каждым коммитом hook автоматически повышает patch (`0.0.1` → `0.0.2`) и синхронизирует `project.godot` и metadata macOS-лаунчера. Поэтому дополнительный коммит внутри одной задачи тоже получает собственную версию.

Обычный commit не требует ручной команды. Для осознанного перехода minor или major заранее выполните `python3 tools/bump_version.py --set 0.1.0`; hook увидит уже повышенную версию и не увеличит её второй раз. Команда `python3 tools/bump_version.py --check` только проверяет синхронизацию и входит в architecture gate.

## Как добавить игровую механику

1. Откройте [карту модулей](MODULE_STRUCTURE.md), определите единственного владельца правил в `scripts/systems` или создайте новую узкую систему.
2. Храните изменяемые данные в подходящей модели `scripts/state`, а статический контент — в data-driven каталоге.
3. Подключите операцию через `game.gd` и `game_context.gd`, не перенося правила в обработчик клавиш или renderer.
4. Добавьте автотест в тематический suite. Он должен описывать сценарий, исходное состояние и ожидаемый результат.
5. Добавьте шаг во внутриигровое обучение и [ручной QA-маршрут](../QA_CHECKLIST.md).
6. Обновите [руководство игрока](GAME_GUIDE.md), если изменилось видимое поведение.
7. Выполните quality gate и, для графических изменений, визуальную проверку в окне игры.

## Контракты кода

- Все методы GDScript имеют непосредственно над объявлением русский комментарий `##`.
- Тестовый метод имеет три строки: `Сценарий`, `Исходное состояние`, `Ожидаемый результат`.
- Система не читает ввод и не рисует; renderer не меняет игровое состояние.
- Предмет регистрируется один раз в `InventorySystem.ITEM_DATA`; другие системы используют его идентификатор.
- Изменение формата сохранения требует новой версии, миграции и теста повреждённых данных.
- Новый suite не превышает 350 исполняемых строк; `game_core` ограничен 750, контекст — 350, renderer — 450, а каждый модуль `scripts/core` — 260 исполняемыми строками.
- Новый мировой объект объявляет геометрию в профильной системе и попадает в `WorldVisualAuditSystem`; renderer только читает профиль и рисует.

Подробные владельцы ответственностей и поток кадра описаны в [ARCHITECTURE.md](../ARCHITECTURE.md).

## Производительность

Эталонный замер ограничен 60 FPS и длится 480 кадров. Запускайте его после изменений обновления кадра, навигации, отрисовки, анимации или большого объёма контента. Результат и условия заносите в [PERFORMANCE.md](../PERFORMANCE.md).

Локальные релизные ворота запускаются отдельно: `zsh tools/smoke_test.sh` проходит 180 кадров реального игрового цикла, а `zsh tools/performance_gate.sh` проверяет 480 кадров с минимальным средним значением 50 FPS. Обе команды входят в GitHub Actions после архитектурной проверки и полного набора автотестов.

Для реального покадрового сравнения используйте `tools/runtime_frame_review.gd` с `-- --profile-town`; для второго режима добавьте `--benchmark-debug-overlay`. Аргумент `--report-dir=res://docs/reports/<итерация>/<до-или-после>` сохраняет все 1400 измерений отдельно от предыдущих отчётов. Запускайте normal и F10 последовательно; `--headless` для этого инструмента запрещён.

CPU-запросы можно проверить отдельно инструментами `tools/geometry_benchmark.gd` и `tools/inspector_benchmark.gd` в headless-режиме. Сохраните старые модули командой `git show <ref>:scripts/systems/<модуль>.gd` во временные файлы, затем передайте геометрии `--baseline-dir=<каталог-с-тремя-модулями>`, инспектору `--baseline=<старый-debug_object_inspector_system.gd>`. Общие аргументы: `--baseline-ref=<ref>` и `--report=<JSON>`. Каждый инструмент прогревается, чередует порядок девяти проб и проверяет совпадение результатов. Отдельный CPU-микрозамер не заменяет проверку FPS настоящего renderer-а.

Для прямого визуального просмотра новых NPC, дыхания в покое и движения напарников используйте `tools/Godot.app/Contents/MacOS/Godot --path . -- --animation-preview`.

## Модульная пещера

Схема второй локации находится в [CaveMapData](../scripts/systems/cave_map_data.gd), сборка стен и навигационный контур — в [CaveLayoutSystem](../scripts/systems/cave_layout_system.gd). Пол и статические элементы кешируются CanvasItem фона. Контактные тени и свет используют один общий радиальный градиент, а renderer жил отсекает элементы вне камеры; PNG, списки стен и полигон не создаются каждый кадр.

[CaveRenderer](../scripts/systems/cave_renderer.gd) рисует отдельные спрайты из [набора](../assets/game/locations/cave/modular/README.md), поддерживает перекрытие героя передними скалами и не использует изображение полного концепта как фон. Жила выбирает самостоятельную текстуру и основание из общего профиля. На поверхность сохраняется прежний профиль ресурсов.

Порядок первых пяти ресурсов сохранён для совместимости массива resource_hits. Четыре новые пещерные жилы добавляются в конец. Загрузка исправляет только позиции, заблокированные новым контуром, декором или жилами, без сброса наград и характеристик. Металлическая жила выдаёт существующий предмет metal.

Кисть редактора получает размер и основание пещерного элемента через [EditorCaveSourceSystem](../scripts/editor/editor_cave_source_system.gd). Смещение основания переводится относительно центра прямоугольника редактора; поле PNG с нижней опорой не становится целиком непроходимым. Для других локаций используются те же PNG и профили.

Проверки маршрутов, добычи, переходов, старых сохранений, инспектора и редактора находятся в [CaveLocationSuite](../tests/suites/cave_location_suite.gd). Нативные кадры сохранены вместе с [исходным концептом](concepts/cave-location-2026-10/v1/README.md).
## Комнаты пещер

[CaveRoomData](../scripts/systems/cave_room_data.gd) задаёт шесть независимых `location` и двусторонний граф туннелей. Линейный `WorldSystem.LOCATIONS` сохраняет прежний порядок наземного маршрута; дочерние комнаты разрешаются реестром контента, относятся к региону `cave` на карте и используют подземную музыку. Внешний переход доступен только из `cave_sanctum`.

[CaveLayout](../scripts/systems/cave_layout_system.gd) кеширует пол, стены, границы их спрайтов, сегменты и водоёмы по идентификатору комнаты. `PATHS` перечисляет соединённые прямоугольные залы и коридоры в порядке присоединения; комнаты объединяются в полигон один раз. Скальная перегородка и водоёмы имеют общий для рисунка и физики контур. Неподвижное оформление принадлежит кешируемому фону, а свечение и вода получают отдельные динамические детали с отсечением камерой.

[CavePassageSystem](../scripts/systems/cave_passage_system.gd) появляется в автоматическом и ручном взаимодействии через `cave_passage:<port>`. Его единственный переход сохраняет мир, перемещает героя на 96 пикселей внутрь обратной двери и перевзводит контроллер только после выхода из её зоны. Существующие индексы жил и противников сохраняются: новые записи [CaveDungeonContent](../scripts/systems/cave_dungeon_content.gd) добавляются после прежних. Отсутствующие в старом снимке жилы и новые враги получают исходные значения; недостающие сундуки восстанавливаются детерминированно.

Выпавший предмет содержит `location`, которую учитывают рисунок, поиск взаимодействия, F10 и подбор. Сохранение проверяет необязательное строковое поле до изменения состояния. Снимок без поля привязывает предмет к своей сохранённой локации. Регрессии и настоящий обход пола находятся в [CaveLabyrinthSuite](../tests/suites/cave_labyrinth_suite.gd), игровые кадры — в [галерее комнат](concepts/cave-labyrinth-2026-10/v1/README.md).

## Проект арены пещерного босса

[Два макета арены](concepts/cave-boss-2026-10/v1/README.md) сохранены отдельно от production-контента. `render.gd` в каталоге концепта использует нативный `SubViewport`, текущий каталог пещерных спрайтов и самостоятельный PNG Хранителя; игровая сцена и `user://` не затрагиваются. Для съёмки требуется графический контекст, `--headless` для этого сценария не используется. Геометрические утверждения проверяют соединённый контур комнаты и размещение героя/декора на сухом полу. Материал пола и воды повторяется через `CanvasItem.TEXTURE_REPEAT_ENABLED`.

Галерея позволяет сравнить планы и четыре состояния. Пока это дизайн-предложение: уникальная награда, запуск через алтарь, две атаки и перенос старого сюжетного врага описаны в концепте; внедрение следует после выбора варианта. В частности, существующий `CombatSystem` ещё трактует всё семейство `cave_guardian` как фазовых врагов и выдаёт реликвию каждому из них.

## Бой Хранителя в святилище — 11 октября 2026

`CaveBossSystem` управляет выделенным врагом с флагом `cave_boss`, сохраняя прежние 37 индексов врагов. Его обычный AI и renderer пропускают; общая система оружия, урона, опыта и добычи сохранена. `CaveBossAttackSystem` задаёт двенадцать геометрий и контактные моменты, `CaveBossMinionSystem` — ограниченные волны и анимации появления, `CaveBossProjectileSystem` — отрезочные попадания и конечные укусы. Симуляция идёт шагами не больше 0,05 секунды. `CaveBossRenderer` использует отдельные атласы и рисует предупреждения под персонажами.

Временное состояние находится в `WorldState.cave_boss`; постоянные HP/позиция/победа остаются в `enemies`. Снимок теперь содержит `max_hp` для безопасного переноса процента HP из прежнего стража. Загрузка очищает временные угрозы и даёт новую передышку; некорректный `max_hp` проверяется до изменения состояния.

Запуск для QA: `tools/Godot.app/Contents/MacOS/Godot --path . -- --cave-boss-preview`. [Спецификация и нативные кадры](concepts/cave-boss-combat-2026-10/v1/README.md). `CaveBossSuite` и `CaveBossMinionsSuite` подключены через боевой агрегатор; отдельный набор спрайтов проверяет все 89 кадров.
