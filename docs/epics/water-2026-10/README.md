## Образ и границы

1. Ось русла состоит только из горизонтальных и вертикальных отрезков на сетке 24×24. Повороты — на 90°, без длинных скошенных берегов. У контура допустима мелкая нарисованная неровность земли; она не меняет проходимую геометрию. Движение персонажа по диагонали не запрещаем.
2. Берег — небольшой самостоятельный элемент: трава/земля → верхняя кромка → срез грунта и мягкая тень → мелководье → основная вода. Не превращать каждую реку в огромную канаву или толстую каменную стену.
3. Для деревни подходит укреплённый участок с камнем/деревянной кромкой, для поля — земля и трава, для пещеры — камень. Одинаковая система стыков и общая вода; различается материал берега.
4. На макетах сравнить **A — мягкий земляной берег** и **B — аккуратная деревенская канава/укрепление**. На обоих показать одинаковый прямой отрезок, поворот, пруд и мост рядом с героем. Сначала выбор, потом игровые PNG. Эти варианты ещё не нарисованы и не выбраны.
5. Вода выглядит убедительно благодаря спокойному течению, глубине и кромке, сохраняя рисованный стиль игры. Фотореализм, постоянный белый шум, резкое мерцание и крупные одинаковые пузырьки не являются целью.
6. Пруд имеет осевой ступенчатый план с небольшими уступами, а не выглядит диагональным продолжением реки. У стоячей воды нет направленного движения через весь водоём.
7. Сохраняем безопасные ограды возле деревенских проходов, доступ к мостам и рыбалке. Новая вода не становится поводом поставить лавочки или телегу в воду.
8. Плавание, лодки, течение, толкающее героя, затопления, гидросимуляция, сезонная проходимость льда и новая экономика рыбы не входят в этот эпик.

## Предлагаемый технический контракт

Решения ниже — проект реализации; их работоспособность и стоимость ещё предстоит проверить.

- **Одна исходная геометрия.** Сетка 24 px хранит водоёмы, осевые соединения N/E/S/W, тип/глубину и направление течения. Из неё строятся берег, маски, визуальная геометрия и пространственные запросы. Для физических проверок сохраняем проектную точность 12 px и реальную форму героя.
- **Разные смыслы запросов.** `water_surface` остаётся под мостом; `walkable_surface` учитывает настил; запрет движения учитывает воду, берег, ограду и радиус объекта. Поплавок ищет видимую доступную воду, а не настил или скрытый участок под мостом. Это производные одного плана, а не независимые нарисованные контуры.
- **Течение не выводится из одного X.** Прямая, поворот, тупик, слияние и стоячая вода имеют явные правила. Контакт по диагонали не соединяет два водоёма. Восьмибитная информация о соседях может использоваться для выбора вогнутых/выпуклых кромок.
- **Маленькие повторяемые ресурсы.** Отдельные береговые PNG/атлас, бесшовный материал поверхности и компактные данные глубины/течения. Не делать уникальную огромную картинку каждой карты. Свет и тень у N/E/S/W рисуются осмысленно: нельзя вращать освещённый берег так, чтобы солнце переезжало вместе с ним. Четыре стороны ландшафта не меняют правило трёх ракурсов мебели.
- **Статика отдельно.** Земля и берег остаются кешируемыми; после миграции их слой не содержит старой неподвижной реки под новой водой. Поверхность воды рисуется отдельными видимыми группами. Изменение времени не инвалидирует землю.
- **Основной кандидат анимации.** Один простой `CanvasItem`-шейдер поверхности: медленное смещение рисунка, небольшая рябь и мягкая полоса мелководья по подготовленной маске. Без экранной копии, полноэкранного преломления, отражающей камеры, real-time SDF и шума с большим числом итераций. Видимость и стоимость проверяются, а не предполагаются.
- **Упрощённый кандидат.** Небольшой циклический атлас, ориентир 8 кадров с 8–12 обновлениями/с, либо уменьшенный шейдер. Точная схема выбирается по прототипу. Уровень качества меняет поверхность, сохраняя берег, контур, коллизии и рыбалку. Reduced motion может остановить декоративное движение, сохранив сигнал поклёвки.
- **Время воды управляется игрой.** Нужен общий ограниченный счётчик/фаза, который останавливается при паузе мира. Шейдерный `TIME` сам по себе паузу не соблюдает; после меню и сна не должно быть скачка, серии догоняющих всплесков или обнуления мира. Косметическую фазу не записывать каждый кадр в сохранения.
- **Группы вместо узла на клетку.** Стартовый кандидат — чанки 16×16 тайлов (384×384 px), видимая область плюс один чанк запаса. Размер подтвердить измерением. Геометрия/маски строятся при входе или редактировании, а не в каждом кадре. Неактивные карты не имеют живого рендера.
- **Ограниченная память.** Один общий набор материалов; кеш геометрии ограничен активной картой и, только если полезно, одной предыдущей. При выходе освобождать собственные ссылки. Не добавлять периодический полный сброс ресурсов или новую очередь очистки в обход уже сделанного обслуживания кешей.

## Бюджеты производительности — пока цели, не результаты

WATER-01 уточняет эти стартовые пределы на эталонной машине и фиксирует до реализации. Увеличивать бюджет задним числом для зелёного отчёта нельзя: изменение цели требует записанного обоснования. Общие ограничения [OPT](../optimization-2026-10/README.md) сохраняются.

| Показатель | Стартовая цель | Как оценивать |
|---|---|---|
| CPU воды в неизменном кадре | p95 ≤0,35 ms, нет обхода всей карты | Отдельный участок обновления/подготовки команд, без ожидания дисплея |
| Цена живой поверхности | Целевой прирост критического времени рендера ≤1 ms при 1920×1080; ≤1,5 ms при 3584×2240 | Сравнить одинаковую сцену и геометрию с движением/без движения; GPU-таймер где доступен. Под VSync нельзя выдавать разность двух средних FPS за точную цену GPU |
| Общий кадр | Сохранить цель normal p95 ≤20 ms; p99/max/длинные кадры публикуются | При внешнем ограничении отдельно показать абсолютный провал общей цели и вклад воды; эпик воды не закрывает TD-PERF-007 |
| Статическая земля | 0 пересборок в обычном неизменном кадре | Инвалидации только по ревизии карты/окружения, не по времени анимации |
| Память новой воды | Ориентир ≤16 MiB дополнительных GPU-ресурсов активной карты с общим набором; CPU-геометрия/маски ≤8 MiB | Измерить фактический импорт/формат/буферы, учитывать общие ресурсы один раз; PNG на диске не равен VRAM |
| Кеш карт | Активная + максимум одна предыдущая, ограниченный объём | После обхода всех карт/100 переключений число ресурсов не растёт с числом заходов |
| Живые детали | Стартовый лимит 32 простых водных эффекта на активную карту | Не считать тайлы воды эффектами; дождь/поклёвка используют понятный приоритет и не обходят предел |
| Фоновая работа | Нет живых водных слоёв неактивных карт; нет накопленной очереди после паузы | Счётчики обновлений, подписок и отложенных операций |

Запускать нативные измерения последовательно, без параллельных тестов/другого Godot на GPU. Условия окна, фокуса и маршрута одинаковы. Помимо игрового режима с VSync использовать отдельную явно подписанную uncapped-пробу для поиска fill-rate, если требуется; она не заменяет игровой результат.

## Что проверили в документации Godot

- [CanvasItem shaders](https://docs.godotengine.org/en/stable/tutorials/shaders/shader_reference/canvas_item_shader.html): встроенное время не приостанавливается с деревом и имеет rollover. Наш вывод — собственная управляемая фаза воды и отдельные проверки паузы/длинного цикла.
- [GPU optimization](https://docs.godotengine.org/en/stable/tutorials/performance/gpu_optimization.html): учитывать материалы, заполнение пикселей, overdraw и стоимость чтения текстур. Наш выбор простого прохода, общих ресурсов и контроль на разных разрешениях — гипотеза до нативного сравнения.
- [Using TileSets](https://docs.godotengine.org/en/stable/tutorials/2d/using_tilesets.html): terrain-соседства и варианты тайлов помогают стыковать покрытия. Это основание для полной таблицы стыков; не требование переписать весь существующий renderer на TileMapLayer.
