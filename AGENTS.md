# Рабочие договорённости

- По завершении согласованных изменений делай отдельные коммиты по смыслу и сразу мержи готовую задачу в локальную `main`. После успешного merge удаляй только её полностью влитую локальную ветку, если она не используется другим worktree. Незавершённые и чужие ветки не трогай.
- В GitHub отправляй `main` пакетами: после каждых 10 завершённых задач, а не после каждого коммита. В последнем коммите задачи указывай trailer `Task-Complete: <ID>`; `python3 tools/task_batch.py status` считает уникальные ID в локальной `main`, ещё не опубликованные в `origin/main`. После десятой задачи выполни проверки и `python3 tools/task_batch.py publish`. Промежуточные коммиты, merge-коммиты и служебные изменения без этого trailer не увеличивают счётчик. До накопления десятки прямо сообщай, что изменения сохранены локально. Отдельная прямая просьба пользователя о push позволяет опубликовать неполный пакет.
- Это постоянное разрешение явно распространяется на основную ветку `main`: после проверок разрешены обычные merge, fast-forward и push в `origin/main` для публикации согласованных изменений. Отдельное подтверждение только из-за обновления `main` не требуется. Пользователь отменил такое требование 18 октября 2026 года; запрет force push и переписывания опубликованной истории сохраняется.
- Перед публикацией выполняй проверки из `TESTING.md`. Коммиты должны содержать соответствующие тесты и документацию. Не объединяй несвязанные изменения в один коммит.
- Не используй force push и не переписывай опубликованную историю без отдельного указания пользователя. Если проверки или push не прошли, исправь доступную причину и явно сообщи, что осталось неопубликованным.
- Новую работу выбирай по ID из [указателя бэклогов](docs/backlog/README.md). Для отдельной задачи создавай ветку `codex/<id-строчными>-<короткое-имя>`, например `codex/opt-02-storage-frame-budget`. GitHub issues для этого плана не требуются. Статусы, зависимости и подтверждения выполнения веди в файлах бэклога; порядок описан в `docs/BACKLOG_WORKFLOW.md`.
- Мебель, верстаки, станки, лавочки, колодцы, телеги и подобные предметы имеют только три основных ракурса: влево, вправо и вниз к игроку. Не рисуй и не подключай диагональный разворот или глухую заднюю сторону. Сохраняй прямую привязку к сетке и пропорции; подробности в `docs/SPRITE_STANDARD.md`. Правило повторно подтверждено пользователем 14 октября 2026 года.
- При наличии нескольких вариантов реализации или дизайна самостоятельно выбирай наиболее подходящий требованиям проекта и продолжай разработку без запроса выбора у пользователя. Это правило заменяет прежние требования ждать пользовательского выбора варианта в документации и карточках бэклога.
- Дизайн-макеты сохраняй отдельно от игровых ресурсов.
- Центр разработки находится в Wiki: меню «Эпики», «Идеи», «На проработку», «Задачи». Решения об идеях и группах сохраняются в `wiki/planning/state.json`; реестр подключённых планов — `wiki/planning/sources.json`. Одобренные идеи (`approved`/`refining`) — очередь постановки для агента; одобрение не означает выполненную реализацию. При подготовке задач сохраняй существующие ID и статусы, регистрируй новые источники и связывай идею с настоящими эпиками. Подробности в `docs/WIKI_DEVELOPMENT.md`.

Договорённость о постоянных commit и push подтверждена пользователем 11 октября 2026 года.
Порядок «готовая задача → локальная main; push после 10 задач» установлен пользователем 18 октября 2026 года и заменяет прежний немедленный push каждого коммита. Обычные commit, merge и push постоянно разрешены, повторное подтверждение не требуется.
